# Messaging

The Showcase story holds the stage, the recipe and a working set of the components. The Advisories story holds the live rulebook and the accessibility coverage. The Examples story holds one recipe per branch of the decision. This guide holds the reasoning.

## 1. Introduction

**In plain words:** Messaging is how the product tells a user something. Most of the time the best message is none. When one is needed, pick the one that interrupts least.

**Precisely:** Pattern. A decision procedure that maps a user need to one of Toast, Banner, a field error, Alert dialog, Confirmation dialog, Popover, Tooltip, Badge or Empty state. It has no style and no token of its own.

**The user need.** Every message competes for attention with everything else on the screen (GitLab Pajamas, Choosing a messaging pattern). The user needs to hear what matters, in the place they are already looking, without losing their work.

**When it exists.** Use it each time you are about to tell a user something. It sits above components in the import order, so only an app or another pattern may compose it.

## 2. Usage

### The decision

Ask the questions in order and stop at the first answer that holds. The core rule is "the least disruptive option that does the job": if the user has to leave their task to receive a signal, the signal is usually in the wrong place.

1. **Does the user need to know at all?** No action is open and no information is needed: show nothing.
2. **Is it the result of an action the user took here?** Result visible: nothing. Wrong value in a field: the field `error`. Result not visible, no follow-up: Toast. Costly or irreversible action: Confirmation dialog.
3. **Does it block progress?** Alert dialog.
4. **Is it a condition of the page or system?** Banner.
5. **Is it help for one control?** Short text: Tooltip. Richer, with a link or action: Popover, opened by a click.
6. **Is it a status or count on an item?** Badge.
7. **Is it standing in for missing content?** Empty state.
8. **Is it an event for later?** Bauhaus has no notification component yet. See the gaps.

### When not to use, and what to use instead

- **Wording an error or an empty state.** Read `patterns/empty-and-error`.
- **Field validation timing and the error summary.** Use the form validation pattern.
- **A wait.** Use a Spinner, Skeleton or Progress, not a message.

### How

- **Show nothing first.** A confirmation for something the user can already see adds noise (Pajamas, question 0).
- **One event, one message.** Do not show a toast and a banner for the same save.
- **Announce, do not steal focus.** A Toast, Banner and Badge live in a live region (WCAG 4.1.3 Status Messages, AA; APG Alert: alerts do not affect keyboard focus). `role="status"` is polite. `role="alert"` is for important, time-sensitive information. Keep a status region in the page all the time and render only its content conditionally, because a region mounted with its text is announced unreliably. An urgent alert that must appear with its text takes focus from the app, so the action inside it is next.
- **Toast.** For a result the user cannot see and does not need to act on: "Draft saved." An automatic close is a time limit (WCAG 2.2.1 Timing Adjustable, A), so a toast is never the only home of information the user needs later. A toast with an action stays until closed. Errors go to the assertive region. State no fixed duration in copy or review: the region owns the default.
- **A failure that needs action.** Use a Banner with the action, or the field error. Pajamas states that a toast cannot hold actions accessibly.
- **Dialogs.** Use one only when the user must answer before going on. The Alert dialog has one action. The Confirmation dialog has a choice, and `destructive` shows a danger confirm first, then Cancel, and starts focus on Cancel. Focus moves inside on open and returns to the opener on close (APG Alert and Message Dialogs, Dialog (Modal); WCAG 2.4.3 Focus Order, A).
- **Tooltip.** A string, so it never holds a link. It is a hint: the control must have its own name and work without it. Its content can be dismissed, hovered and stays visible (WCAG 1.4.13 Content on Hover or Focus, AA).
- **Popover.** Opens on click only, so keyboard and screen reader users reach what is inside (Pajamas). Escape closes it and returns focus to the trigger.
- **Colour.** Status has an icon and a word. A Badge has text (WCAG 1.4.1 Use of Color, A).

## 3. Why the states look as they do

- **Nothing is the best message.** No component is the first answer on purpose.
- **Loading is not a message.** A wait has its own components; the pattern does not cover it.
- **None, one, some and too many are n/a.** The pattern is a decision, not a list.
- **Incorrect has two homes.** A wrong value is a field error. A failed request is a Banner with a retry, or an Alert dialog when it blocks.
- **Done is a Toast or nothing.** If the result is visible, say nothing.

## 4. Pitfalls and don'ts

- **Do not use a toast for an error that needs action.** It times out and cannot hold an action accessibly. (Pajamas; WCAG 2.2.1, A; `messaging.toast-not-for-errors-needing-action`)
- **Do not put essential information in a tooltip.** It is a hint, and the control must work without it. (Pajamas; `messaging.no-essential-in-tooltip`)
- **Do not open a popover on hover or focus.** (Pajamas; `messaging.popover-on-click`)
- **Do not show two messages for one event.** (Pajamas; `messaging.one-per-event`)
- **Do not use `role="alert"` for routine news.** It is for time-sensitive information. (APG Alert; `messaging.assertive-only-when-urgent`)
- **Do not use a dialog for a message the user can ignore.** A dialog interrupts the workflow. (APG Alert Dialog; `messaging.least-disruptive`)
- **Do not announce nothing.** A silent message misses screen reader users. (WCAG 4.1.3, AA; `messaging.announced`)
- **Do not add a stylesheet to the pattern folder.** (`docs/library.md`; `messaging.no-own-style`)

## 5. Component gaps

- No notification centre. Pajamas routes events users catch up on later to Notifications. Until one exists, use a Badge on the entry point and a page for the list.
- No drawer and no feature-discovery component. Pajamas routes long help and first-use guidance there.
- No inline-alert component. A Banner inside the content area plays that role.
